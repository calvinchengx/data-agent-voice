The gap this is built around

A question to data-agent-service takes twenty-six seconds at the median — six to eight careful model turns. A conversation reads as broken after about one second of silence.

26smedian, one question
~800msbefore it feels slow
30×the gap
89checks on the design

No faster model closes that. So this does not try to: the conversation stops waiting.

  • A small model owns the turn and speaks before any tool resolves, so first audio arrives in under a second whatever was asked.
  • Definitional questions never reach the warehouse. "What counts as resolved?" is one catalog hop — about a second, no SQL, no waiting.
  • The slow agent runs where nobody is waiting, narrating its progress and speaking its answer when it has one.
  • A refusal is never narrated. Refused, abstained and answered are three distinct events; the first two are spoken from fixed phrases the model never sees.

A backend is a file, not a code path

The line knows kinds of capability — a fast lookup, a dispatch, a terminal outcome — and never a capability's name. Adding a second service is a descriptor:

{
  "name": "data-agent",
  "dispatch": { "tool": "ask_data",
                "description": "Questions needing numbers, tables or metrics." },
  "fast_tools": [{ "name": "glossary_lookup", "budget_ms": 400 }]
}

The host's model routes between backends by their tool descriptions, in the same turn, at no extra latency. A check in the suite fails if any general layer starts naming one service's vocabulary.

What is actually true today

No audio has ever been through this. Four extensions the graph names are not written yet. What exists is the architecture, the pinned framework read from its source, a multi-arch image, the graph, and 89end-to-end witnesses holding the configuration to itself.

Every row of the ledger that describes a working line reads not run. That is the point of keeping one.
